## Context

`courier-notices` (v1.9.18, wordpress.org, 40+ active installs, plus Linchpin client sites) is a 2019-era codebase that has been *maintained* rather than modernized. It works, but it is architecturally stranded:

- **The block editor is explicitly turned off.** `Courier_Notice_Metabox::disable_block_editor()` returns `false` for `use_block_editor_for_post_type`, the CPT is `show_in_rest => false`, all 5 taxonomies omit `show_in_rest`, and there is **zero** `register_post_meta`.
- **Notice design lives in a bespoke "Design Studio."** Per-type colors live as `courier_type` term meta, compiled into a CSS string by `Courier_Types::save_css_transient()`, cached in a non-expiring `courier_notice_css` transient, injected with `wp_add_inline_style()`. **No CSS custom properties anywhere**, no border/shadow/spacing control at all, and a *second* parallel color system as compiled SCSS defaults in `assets/scss/shared/_notices.scss`. The plugin cannot inherit a theme.
- **Placement is hook-injection only.** `Placement.php:22-24` hooks `wp_body_open` (header + modal) and `get_footer` (footer). `get_footer` **does not fire at all** in many block themes, so footer notices are silently broken on modern sites. No way to put notices in a template.
- **"Display type" barely exists.** It's smeared across two taxonomies — `popup-modal` is simultaneously a `courier_style` term *and* a `courier_placement` term, the metabox hides the `popup-modal` placement term (`Courier_Notice_Metabox.php:171-179`), and `Data::get_global_notices()` special-cases `'modal' !== $args['placement']`.
- **jQuery admin, vendored 2016 jQuery Timepicker, a 1,449-line fork of `WP_List_Table`, a forked div-based `do_settings_sections()`.**
- **Zero tests.** `phpunit.xml` points at a `tests/` directory that does not exist. PHPStan level 8 with a **105 KB baseline**.

**Intended outcome:** a 2.0.0 that is block-first, theme-aware, and genuinely extensible — with a real display-type system (toast, snackbar, carousel, modal, banner) authors control from the block editor — shipped in place on the same slug, safe for every existing install, with Courier Pro's integration surface intact.

## Render strategy and caching — read this first

**This is the section revision 1 was missing, and it constrains everything else.**

The current architecture is deliberately full-page-cache-proof, and that was a correct decision:

- PHP renders **empty placeholder containers** (`Functions.php:198,229` → `View::get_text_view('notices-ajax')`).
- `assets/js/frontend/core.js` lazy-fetches via REST on `IntersectionObserver`.
- Anonymous dismissals are filtered **client-side** against the `dismissed_notices` cookie (`core.js:111-113,192-198`).
- `prevent_ajax_cache` appends a timestamp buster (`core.js:139-142`).
- There is shipping **WP Rocket compat code** (`courier-notices.php:194-249`) telling admins to exclude the REST route from caching.

A naively server-rendered block reverses all of it. On a page-cached site — which is most production WordPress, including every Pressable/WP Rocket install — notices get baked into cached HTML: new and expired notices frozen until purge, and **one visitor's dismissal state and Pro visibility results served to everyone.**

So the block carries an explicit, author-visible render mode:

| `loading` | Behavior | When |
|---|---|---|
| `lazy` **(default)** | SSR the region shell + Interactivity config only; fetch notice content from the (fixed) `display/all` endpoint inside the store | Any page-cached site. Preserves the WP Rocket guidance, `prevent_ajax_cache`, and the `has_notices` fast-path (`Courier_Notices.php:107`, `Functions.php:322`) |
| `server` | Render notices inline at request time | Uncached or personalized sites; also what `ServerSideRender` shows in the editor preview |

Two hard rules that follow:

1. **`server` mode must emit user-agnostic output only.** Dismissal-hiding happens client-side via Interactivity state in *both* modes. That means removing the cookie read from the cached query path — `Data.php:397-398` currently reads `$_COOKIE['dismissed_notices']` **server-side inside a cached query**, keyed without the cookie. That leak exists today, masked by the client-side re-filter the plan would otherwise delete.
2. **`lazy` mode causes CLS for above-the-fold banners.** A header banner that arrives after paint shifts the page. Reserve space via `min-height` on the region, or steer authors to `server` for banner placements. This is a real reason the mode must be author-visible rather than inferred.

**Performance budget** (set numbers now, assert in CI):

- `view.js` module ≤ 8 KB gzipped
- **Zero** vendor libraries (Swiper, etc.) on pages with no region requiring them
- Notice CSS ≤ 6 KB gzipped
- No CLS regression on a page with a header banner region

## The Courier Pro contract

Pro (private, v1.7.2, 40 open issues) is actively sold and integrates *only* through these. Verified against `linchpin/courier-pro@master`.

**Filters Pro consumes:** `courier_notices_display_notices_query` (`Data.php:372`, 2 args), `courier_notices_allowed_settings` (`Settings.php:50`), `courier_notices_admin_data` (`Admin.php:302`), `courier_notices_admin_strings` (`Admin.php:278`), `courier_notices_localized_data` (`Courier_Notices.php:120`), `courier_notices_settings_tabs` (`General.php:533`), `courier_notices_settings_links` (`General.php:152`), `courier_notices_plugin_title` (`templates/admin/settings.php:34`), `courier_notices_admin_tab_{$tab}_url` (`settings.php:78`), `courier_notices_safe_markup` (`Utils.php:62`).

**Actions Pro consumes:** `courier_notices_setting_{$tab}` — dynamic; Pro registers `license`, `gravityforms`, `changelog`, `changelog_pro`, `whats_new`, `whats_new_pro`.

**Pro also owns:** the `courier_courier_rule` taxonomy, the `courier_visibility_rules` taxonomy that free queries at `Data.php:447,558` and `Functions.php:350` but never registers, and a slide-in display type.

### Preserving `courier_notices_display_notices_query` is harder than "call the same function"

Revision 1 claimed that routing the block through `Data::get_notices()` was sufficient. It isn't. Three concrete breaks, all verified:

**(a) The second argument arrives empty of everything Pro needs.** On the live path `$ajax_post_data` is the *client-posted request params* — `Courier_REST_Controller.php:259` does `wp_parse_args( $request->get_params(), $defaults )`, carrying `post_info` (the visitor's current page, from `courier_notices_data.post_info` at `Courier_Notices.php:99-101`) and `user_id`. A visibility engine deciding "show on page X to role Y" reads exactly that. A block's `render.php` calling `get_notices( $args )` passes `[]`, which `Data.php:287` parses to defaults with **no page and no user**. The filter fires with correct arity and no world.

> **Required:** the block query path synthesizes an `$ajax_post_data`-shaped array from server context — `post_info => [ 'ID' => get_queried_object_id() ]`, `user_id => get_current_user_id()`, plus placement and format. `HookContractTest` asserts the **shape and content** of that second argument, not just that the filter fired.

**(b) The filter is bypassed on every cache hit.** `Data.php:289-304` builds a cache key from `$args` + `$ajax_post_data` and returns from object cache or transient **before** reaching line 372. The cached value embeds whatever the filter did at write time. Anything Pro varies on that isn't in those two arrays — role, time window, referrer — is frozen for 10 minutes and served to everyone with matching args. `HookContractTest` will be green while the feature is broken warm.

> **Required:** a `courier_notices_query_cache_context` filter that Pro contributes to, folded into the cache key. Alternatively move caching above the personalized layer. Decide in Phase 1, not later.

**(c) Post-filter clobber.** `Data.php:373` runs `wp_parse_args( $args, $query_args )` *after* the filter, so `$args` keys silently overwrite filter output on collision and leak non-`WP_Query` keys (`user_id`, `include_global`, `style`) into `WP_Query`. Preserving this line preserves a booby trap; removing it changes filter semantics. Decide explicitly and cover it in the contract test.

**Phase 0 task (not a blocker — Pro work happens in tandem):** read `courier-pro`'s `application/Controller/Addons/Visibility/Visibility.php::filter_courier_notifications()` to pin down which `$ajax_post_data` keys it touches, so the synthesized array is a superset of what Pro needs. If the answer arrives late, build the array from what the *free* plugin needs (`post_info`, `user_id`, placement, format — the same keys `Courier_REST_Controller.php:259` posts today) and widen it when Pro's side lands.

### Pro version handshake — release checklist, not a design constraint

Pro is modernized in tandem by the same author and the client footprint is small, so the "free 2.0 auto-updates onto Pro 1.7.2" scenario is a coordination problem rather than a hazard to engineer around.

- Ship the two releases together; note the pairing in `readme.txt` as a compatibility matrix.
- Still implement a **minimum-Pro-version check that pins legacy mode** — it's cheap, and it protects the wp.org installs we don't control if the releases ever drift.
- Skip the reciprocal Pro-side check unless it's free to add.

**[corrected] The slide-in template claim from revision 1 was wrong.** Revision 1 asserted the `courier_style` slug → `templates/notice-{slug}.php` auto-map "is how Pro's slide-in works today." It cannot be: `View::validate_and_build_path()` (`includes/Core/View.php:158-167`) calls `realpath( COURIER_NOTICES_PATH )` and rejects any view dir not prefixed by it, returning `''` silently. `courier-pro/templates/notice-slide-in.php` is unreachable through `Core\View`. Either Pro renders slide-ins by some other mechanism, or **Pro's slide-in has been silently broken since free 1.8.0 shipped that validation** (the validation is `@since 1.8.0`; Pro is 1.7.2). Verify in Phase 0. Design consequence: the display-type registry takes an **explicit absolute template path or render callback**, validated against an allowlist of registered plugin directories — not slug-magic that apparently can't serve the one external consumer it exists for.

## Display types — the new feature

Two orthogonal axes, today tangled into one taxonomy.

### Axis 1 — Presentation

| Slug | Behavior | Positionable |
|---|---|---|
| `inline` | Flows in the document where the block sits | no |
| `banner` | Full-bleed bar, typically header/footer | edge-anchored |
| `modal` | Overlay + focus trap. Rich block layout, imagery, CTAs | centered |
| `toast` | Small floating card, auto-dismiss timer, stacks | yes |
| `snackbar` | Single-line, bottom-anchored, optional action | yes |
| `slide-in` | *Pro* — registers into the registry | yes |

### Axis 2 — Flow

`stack` (up to `maxVisible`, dismissing promotes the next) · `queue` (one at a time) · `rotate` (Swiper carousel, `slidesPerView` at a time, autoplay) · `all` (no cap).

### The honest matrix — not every combination is coherent

Revision 1 oversold this as "all just attribute combinations." It isn't, and shipping the full cross-product would be a support-ticket generator. The registry declares `supported_flows[]` per presentation and **the editor validates**:

| Presentation | Allowed flows | Why the rest are excluded |
|---|---|---|
| `inline` | stack, all | — |
| `banner` | stack, rotate, all | — |
| `toast` | stack, queue | — |
| `snackbar` | queue | "single-line, bottom-anchored" contradicts stacking |
| `modal` | queue | Multiple simultaneous `alertdialog`s = competing focus traps, an a11y violation. A carousel of focus-trapped overlays is not a thing. |

Two more guards:

- **`queue` + not dismissible + no auto-dismiss = deadlock** — notice 2 never appears. Enforce `dismissible || autoDismiss` when flow is `queue`.
- **`autoDismiss` on `modal` fails WCAG 2.2.1.** Presentations can veto shared controls; the registry entry carries the veto list.

### Per-notice vs per-region precedence — needs deciding, not deferring

Today presentation is **per-notice**: the `courier_style` term selects the template, and `popup-modal` is literally a style term. The block makes it **per-region** via a `displayType` attribute. Both cannot silently coexist.

**Decision:** the block's `displayType` wins **and doubles as a query filter** — a region renders only notices whose `courier_style` is compatible or unset. A notice authored as `popup-modal` does not get coerced into a toast region; it simply isn't selected by it. In modern mode `courier_style` is repositioned as "which presentations may render me," with a migration mapping existing terms.

### Shared controls

- **Screen position** — 6 anchors (`top-left|top-center|top-right|bottom-left|bottom-center|bottom-right`). *Cut from 9: `middle-*` toasts are dead surface.* Follows the enum convention in `linchpin-blocks/blocks/src/slider-controller/block.json`.
- **`maxVisible`**, **`flow`**, **`autoDismiss` + `autoDismissDelay`**, **`dismissible`** (region-level is a ceiling, not an override), **edge offset** using theme.json spacing presets.

### Design controls — borders, shadows, and the rest

Today there is no border or shadow control anywhere. 2.0 gets them via **block supports**, which is also what makes theme.json apply for free:

```json
"supports": {
  "color":      { "text": true, "background": true, "gradients": true, "link": true },
  "spacing":    { "padding": true, "margin": true, "blockGap": true },
  "typography": { "fontSize": true, "lineHeight": true, "__experimentalFontFamily": true },
  "shadow": true,
  "__experimentalBorder": { "color": true, "radius": true, "style": true, "width": true },
  "dimensions": { "minHeight": true },
  "layout": true,
  "interactivity": true
}
```

Per-notice-type design stays available but migrates from term meta → CSS custom properties, so borders and shadows are token-driven and a theme can restyle everything from `theme.json` `styles.blocks['courier/notices']`. Floating regions get a `--courier-z` token rather than a hardcoded `z-index`, so themes with sticky headers can adjust.

*Cut to 2.1:* named block style variations (Outlined/Filled/Soft/Elevated) — tokens plus supports already deliver theming. *Cut entirely:* the `styleSource: inherit|override` attribute from revision 1 — block supports already behave that way (explicit wins, unset falls through to tokens); a mode switch is a second way to reach every state.

### Carousel and vendor libraries — shared externals

Reuse the house pattern (`linchpin-blocks/blocks/src/slider-controller/view.js:153`, `blocks/webpack.config.js`): **Swiper 12** as a webpack external (`swiper: 'Swiper'`), UMD bundle copied by `CopyWebpackPlugin` to `build/swiper.min.js`, driven from `callbacks.onNoticesInit` via `new window.Swiper( container, opts )`. Dismissal calls `swiper.removeSlide()` + `swiper.update()` then persists through the dismissal endpoint.

**Every third-party runtime library is an external, never bundled** — the contract linchpin-blocks already uses (`swiper`, `gsap`, `three`, `postprocessing`, `lodash`). Two things it doesn't solve, because it's the only plugin in the room:

1. **Shared handles so two plugins cooperate rather than double-enqueue.** Register under plugin-neutral handles — `linchpin-swiper` — and guard:
   ```php
   if ( ! wp_script_is( 'linchpin-swiper', 'registered' ) ) {
       wp_register_script( 'linchpin-swiper', $url, [], $ver, [ 'in_footer' => true ] );
   }
   ```
   Whichever plugin loads first wins. Add a `courier_notices_vendor_script_url` filter so a site, Pro, or a theme already shipping Swiper can redirect the handle. **Lifting this convention back into `linchpin-blocks` is a follow-up task in the Linchpin Blocks space — 2.0 does not block on it.**
2. **Conditional enqueue** via `has_block()` + attribute inspection, or a render-time flag consumed on `wp_enqueue_scripts` at `PHP_INT_MAX`. Non-negotiable given the performance budget.

**Scope cut:** `rotate` ships for `banner` and `inline` only. Carousel-of-toasts has no user, and rotating notices carry WCAG 2.2.2 pause/stop/hide obligations.

**On Sonner:** it's a React component library; the Interactivity API frontend is Preact signals, not React — it can't drive frontend toasts without shipping React to the front end. Split:

| Need | Library |
|---|---|
| Frontend toast/snackbar enter/exit, stack reflow | **CSS transitions + `@starting-style`.** Zero JS weight, degrades correctly under `prefers-reduced-motion` |
| Carousel | **Swiper** (external, shared handle) |
| Toasts inside the React admin | `@wordpress/components` `Snackbar` + `@wordpress/notices` (what mantle uses), or Sonner |

**GSAP is cut from 2.0** — CSS-first covers the motion we need; don't wire an external nobody calls.

### Accessibility — non-negotiable, and `plugin-check` tests it

`role="status"` + `aria-live="polite"` for toast/snackbar; `role="alertdialog"` + focus trap + `Escape` + focus restoration for modal; no auto-dismiss or rotation under `prefers-reduced-motion`; pause-on-hover/focus; visible dismiss affordance with an accessible name.

### Robust notices and the Block Bindings API — reframed

Revision 1 called per-notice bindings inside a render loop "the single hardest technical unknown." **It's a known quantity** — it's exactly what `core/post-template` does, using public API:

```php
( new WP_Block( $parsed_layout, [ 'postId' => $notice_id, 'postType' => 'courier_notice' ] ) )
    ->render( [ 'dynamic' => false ] );
```

The second constructor argument is per-instance available context. Two payoffs revision 1 missed:

1. Because a notice **is a post**, providing `postId`/`postType` makes core's `core/post-title`, `core/post-content`, `core/post-featured-image` and the built-in `core/post-meta` binding source work in a notice shell with **zero custom binding code**.
2. A custom `courier/notice` source is then only needed for courier-specific values (type label, icon, `expiresAt`), registered with `uses_context => ['courier/noticeId']` — the same shape as `linchpin-blocks/includes/Controller/Block_Bindings.php`.

`render_block_context` (WP 6.5+) is the escape hatch if constructor context proves insufficient for deeply nested shells.

**Still timebox a spike** in Phase 3 for the two genuine unknowns: bindings' limited supported-blocks/attributes allowlist, and editor preview inside a shell showing placeholders.

**The token-substitution fallback from revision 1 is deleted.** It forfeits editor fidelity and invents a parallel templating language we'd maintain for a decade. The real fallback is narrower: *shell uses core post blocks only, no custom binding source in 2.0.*

**Classic themes:** "design the shell once in a template part" requires the Site Editor. Classic themes are explicitly supported (via the `wp_interactivity_process_directives` fallback), so the shell container is a **synced pattern (`wp_block`)** — editable everywhere — not a template part.

Adopt `mantle` / `linchpin-blocks` conventions; skip what both explorations flagged as anti-patterns.

### Build

Single npm workspace. `@wordpress/scripts` `^30.21.0` → `^34`.

```json
"build": "wp-scripts build --blocks-manifest --webpack-copy-php --experimental-modules --webpack-src-dir=src"
```

`--blocks-manifest` → `build/blocks-manifest.php`; `--webpack-copy-php` → copies `render.php` into `build/<slug>/`; `--experimental-modules` → `viewScriptModule` emits real ESM with `'type' => 'module'`.

Source moves `assets/` → `src/`; output moves from the **committed** root `js/`+`css/` → an **uncommitted `build/`**:

```
src/
├── blocks/notices/    { block.json, index.js, edit.js, render.php, view.js, controls/, style.scss, edit.scss, variations.js, bindings.js }
├── admin/             React screens
├── editor/            PluginDocumentSettingPanel for the CPT
├── slots/             createSlotFill definitions
└── scss/
```

`webpack.config.js` spreads `getWebpackEntryPoints()`, adds explicit `admin`/`editor`/SCSS entries, and carries the shared vendor externals contract.

**Migration trap:** committed `js/`/`css/` are referenced by `Courier_Notices::wp_enqueue_styles()`, `Admin::admin_enqueue_styles()`, `.distignore`, and `wordpress-plugin-deploy.yml`. All four change together or the wp.org SVN deploy ships an empty plugin.

## Backwards compatibility

`courier_notices_options['rendering_mode']` ∈ `modern` | `legacy`, plus a `courier_notices_rendering_mode` filter.

**Auto-detect must run on `plugins_loaded`, front and admin — not admin-only.** `Upgrade::upgrade()` fires on `admin_init`, but wp.org auto-updates happen with no admin visit for days; an ungated site would render modern (wrong) until someone logs in. Treat "mode unset + 1.x fingerprint present (`courier_settings` exists)" as legacy.

**Rev 3 simplifies the detection.** Rev 2 proposed five heuristics including `has_filter()` probing and term-meta diffing against seeded defaults. With a very small client footprint and ~40 wp.org installs, that machinery costs more than it buys — and the `has_filter()` probe had a known false negative anyway (a theme registering the filter conditionally, front-end only, evades a gate-time check).

**Use one signal:** does a 1.x fingerprint exist? `courier_settings` or `courier_notices_options['plugin_version']` present → **`legacy`**. Absent → **`modern`**. Fresh installs get modern; every upgraded site gets the zero-visual-change path and flips deliberately from the settings screen.

Additionally pin to `legacy` when **Pro is below the minimum version** — cheap insurance for the wp.org installs we don't control.

This trades a little precision for a lot less code, and the failure mode is benign: a site that could have gone straight to modern lands on legacy and flips with one click.

**Legacy layer:** `Placement` keeps `wp_body_open` + `get_footer` in Legacy mode unchanged. Modern mode **also** hooks `wp_footer` — the actual fix for the block-theme breakage — **and that ships in Phase 3 with the placement work, not Phase 7.** Both shortcodes stay registered and deprecate loudly (remove in 3.0); note `[courier_notices]` is broken today (the `sprintf()` at `Shortcodes.php:77` is never echoed) — fix rather than carry forward. All 12 deprecated globals in `Helper/Deprecated.php` stay.
